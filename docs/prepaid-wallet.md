# 웹 선충전 결제 전환

기준: origin/master `4f1db2d`. 운영 코드·DB에는 접근하거나 변경하지 않았다. 배포·병합하지 않는다.

## 조사

- 웹 `OrderController`와 `/api/v1/orders`의 `OrderApiController`는 `OrderPlacer`를 공유한다. API 인증은 API 키 소유 회원을 주문자로 연결한다.
- 기존 주문은 `pending`(접수)으로 생성되고, 관리자 `/admin/orders` 상세의 승인·발주에서 외부 업체 전송과 `processing` 전환을 수행한다. 별도 입금 확인 레코드나 결제 상태는 없으며, 주문 완료 화면에서 계좌 안내 후 담당자가 입금과 주문을 대조하는 구조다.
- `BankAccount`는 `AppSetting`의 기존 암호화된 은행·계좌·예금주 설정을 읽는다. 새 충전에서도 이 설정을 재사용한다. 환경설정 파일 수정은 없다.
- 회원 마케팅 주문용 잔액·캐시·원장은 없다. 리워드 참여자의 포인트 제한은 별도 도메인으로 회원 결제에 재사용할 수 없다. 쿠폰만 기존 기능을 그대로 사용한다.
- 기존 `total_price`는 공급가액이다. `Vat::total`이 계산하는 부가세 포함 원 단위 금액을 차감한다. 예: 공급가 1,000원 → 잔액 1,100원 차감. 충전 5,000원 입금 → 잔액 5,000원 증가(충전 시 세금 재가산 없음).

## 웹 동작

1. `/wallet`: 금액·입금자명으로 충전 요청 생성. 요청별 `RF…` 코드와 기존 무통장 계좌 표시. 계좌 미설정 시 요청 생성 차단.
2. `/admin/topups`: 실제 입금과 금액·입금자명/요청 코드를 대조한 뒤 확인 또는 거절. 기존 관리자 호스트·로그인·운영자 권한을 적용한다. 확인 시 회원 잔액 증가와 원장 기록, 요청 상태 및 처리자·시간 저장을 한 트랜잭션에서 수행한다. 재확인은 오류 처리한다.
3. 웹 주문만 서버가 `prepaid=true`를 전달한다. 주문·쿠폰 사용·VAT 포함 잔액 차감을 같은 트랜잭션에서 수행한다. 부족하면 주문과 쿠폰 사용을 모두 롤백하고 충전 화면 링크로 안내한다. 성공하면 결제가 끝난 접수(`pending`)이며 재입금 안내를 표시하지 않는다. 외부 업체 발주는 기존 관리자 승인 절차를 유지한다.
4. 관리자 취소·거절·삭제는 최초 차감액을 한 번만 환원한다. 원장은 주문 삭제 후에도 보존한다. 환원된 주문의 재진행·재발주를 막는다. 쿠폰 복원은 현재 해당 주문에 연결된 사용분만 복원한다.
5. 잔액 결제 주문의 수량·기간은 변경하지 못한다. 금액 변경이 필요한 경우 취소·환원 후 새로 주문한다. 기존 주문의 수정 흐름은 유지한다.
6. 회원 화면은 본인의 충전 요청·원장만 조회한다. 콘솔 공통 메뉴와 주문 화면에 잔액·충전 링크가 있고, 관리자 주문 목록에서 충전 요청 관리로 이동한다. 주문 상세에서 잔액 결제와 기존 주문/API 주문을 구분한다.

## 전환 및 API 호환

`OrderPlacer`의 기본값은 기존 주문 방식이다. API가 웹 선충전 옵션을 전달하지 않으므로 API 키 소유 계정의 웹 잔액을 차감하지 않는다. API 요청/응답·인증·기존 상태·외부 발주 동작을 유지한다. 셀프마케팅 앱은 앱 서버 잔액으로 이미 별도 관리하므로 랭크프리에서도 차감하면 이중 결제 및 잔액 0원 API 계정의 주문 장애가 발생한다. 추후 API 선충전 전환은 별도 계약과 앱 서버 정산 변경이 필요하다.

전환 전 웹 주문 및 기존 API 주문에는 `order:{id}` 차감 원장이 없다. 기존 승인·발주·취소 절차를 유지하고 웹 잔액을 임의 적립하거나 환원하지 않는다. 과거 주문을 마이그레이션으로 잔액 결제로 바꾸지 않는다.

## 무결성

- 회원의 기존 `users` 행을 `SELECT … FOR UPDATE`로 잠근 후 현재 잔액을 읽고 음수 여부를 검사한다. 신규 지갑 생성 경쟁이 없다.
- 차감·충전·환원과 원장의 `balance_after`를 동일 트랜잭션에서 저장한다. 원장 `reference` 고유 제약으로 요청 확인·환원 중복을 막는다.
- 충전 확인은 충전 요청 행, 취소·삭제는 주문 행도 잠근다. 주문 트랜잭션은 데드락/잠금 충돌을 최대 5회 재시도한다.
- SQLite 파일 DB와 독립 연결을 쓰는 두 실제 프로세스 동시 주문 테스트를 포함한다. 로컬에 MySQL 서버가 없어 MySQL/InnoDB 엔진 자체의 병렬 실행은 검증하지 않았다.

## PR #15 검수 보완: 발주와 환원

모든 외부 발주는 OrderDispatchState의 주문 행 잠금으로 pending/processing → dispatching 전이를 커밋한 뒤 실행한다. 일반·세부·예약·재전송은 OrderDispatchService의 실제 send 직전, 부스팅샵 플레이스/쇼핑은 API 호출 직전에 같은 전이를 사용한다. 발주 기록 생성 자체는 외부 전송이 아니므로 취소가 먼저 완료되면 기록은 canceled로 남고 업체 호출은 생략한다.

취소·거절·삭제도 동일한 주문 행 잠금을 사용한다. dispatching 상태의 변경 및 삭제를 거절하고, 선충전 차감이 있는 processing 주문의 자동 환원을 거절하여 관리자 확인으로 넘긴다. 차감 원장이 없는 기존 주문의 취소 동작은 유지하며 잔액을 적립하지 않는다. 전송 완료는 잠금 안에서 최신 dispatching 상태에만 적용한다. 미래 회차 승인도 최신 pending 상태만 활성화한다. 부스팅샵의 명시적인 실패는 발주 전 상태로 복귀하며, 호출 결과를 알 수 없는 예외는 processing으로 남겨 확인하게 한다. 프로세스가 강제 종료되어 dispatching에 남은 주문도 자동 환원하지 않고 관리자 확인이 필요하다.

v1 API는 rejected를 canceled(취소), dispatching을 processing(진행중)으로 직렬화하며 기존 필드를 유지한다. canceled/processing 목록 필터는 대응하는 내부 상태도 포함하고 rejected/dispatching은 v1 필터 값으로 인정하지 않는다(기존 미지원 필터처럼 무시).
