# 퀴즈농장 서버 API 명세

미니앱 클라이언트가 호출하는 우리 서버 API입니다.
**미션 내용·연결 링크·정답 채점을 전부 서버가 담당**합니다.

## 왜 서버가 해야 하나

| 항목 | 이유 |
|---|---|
| 미션 목록 | 앱 재배포 없이 문제·링크·보상을 교체할 수 있어야 함 |
| 힌트 링크 | 광고주/상품이 바뀌면 링크만 갈아끼움 |
| **정답 채점** | 정답을 클라이언트에 내려주면 조작 가능. **절대 내려보내지 않음** |
| 중복 지급 방지 | 로컬 저장소는 사용자가 조작할 수 있음 |

## 앱인토스 환경 제약 (필수)

- **HTTPS 전용.** HTTP API는 토스앱에서 차단됩니다.
- **쿠키 세션 불가.** iOS 13.4+ 에서 서드파티 쿠키가 완전 차단됩니다 → 헤더 토큰 방식만 가능.
- **CORS 허용 Origin 등록 필수:**
  - `https://<appName>.apps.tossmini.com` (실서비스)
  - `https://<appName>.private-apps.tossmini.com` (QR 테스트)
  - ※ 일부 문서는 `.web.tossmini.com` 표기 → **콘솔에서 실제 값 확인 후 둘 다 등록 권장**
- 서버 간 통신(프로모션 지급 등)은 **mTLS 인증서** 필요, 분당 3,000 QPM 제한.

## 인증

클라이언트는 앱인토스에서 발급받은 사용자 식별키를 헤더로 보냅니다.

```
x-user-key: <getAnonymousKey() 결과 또는 토스 로그인 기반 사용자 키>
Content-Type: application/json
```

서버는 이 키로 사용자를 식별하고, 키가 없거나 위조되면 401을 반환합니다.

## 0. 운영 설정

```
GET /config
```

쿨타임·하루 참여 횟수·지급 포인트처럼 **운영하면서 자주 바뀌는 값**입니다.
앱을 다시 배포하지 않고 바꿀 수 있도록 **rankfree 관리자 환경설정**에서 정하고 여기로 내려줍니다.

**응답 200**

```json
{
  "cooldownMinutes": 120,
  "dailyMissionLimit": 3,
  "pointsByCrop": {
    "lettuce": 50,
    "carrot": 70,
    "onion": 70,
    "potato": 100,
    "tomato": 150,
    "corn": 200
  },
  "defaultPoints": 50,
  "maxPointPerUser": 5000
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `cooldownMinutes` | number | 미션 참여 사이 최소 간격 (분) |
| `dailyMissionLimit` | number | 한 사람이 하루에 참여할 수 있는 횟수 |
| `pointsByCrop` | object | 작물 id → 수확 시 지급 포인트 |
| `defaultPoints` | number | 목록에 없는 작물의 기본 지급액 |
| `maxPointPerUser` | number | 1인 누적 지급 상한 (프로모션 정책상 5,000) |

일부 필드만 내려줘도 됩니다. 클라이언트가 나머지를 기본값(`DEFAULT_CONFIG`)으로 채웁니다.

> ⚠️ **이 값들은 화면 표시용입니다.**
> 쿨타임 초과·횟수 초과·지급 금액은 **서버가 제출·수확 시점에 다시 검증**해야 합니다.
> 클라이언트가 받은 설정은 조작될 수 있습니다.

**캐싱** — 하루 100만 참여 규모라 매 요청 DB를 치면 안 됩니다.
설정은 캐시에 올리고 관리자가 저장할 때 무효화합니다.
관리자 화면 구성과 저장 흐름은 `farm-admin-settings.md`를 보세요.

### 설정을 바꾸면 진행 중인 데이터는 어떻게 되나

| 변경 | 처리 |
|---|---|
| **쿨타임 단축** | 이미 발급된 `nextMissionAt`은 **그대로** 둡니다. 소급 적용하면 사용자가 안내받은 시각보다 일찍 열려 혼란스럽고, 예약해 둔 알림과도 어긋납니다. 다음 참여부터 새 값 적용 |
| **쿨타임 연장** | 동일. 진행 중인 건은 건드리지 않습니다 |
| **하루 횟수 축소** | 이미 그 이상 참여한 사용자는 남은 횟수가 0이 될 뿐이고, **이미 지급한 보상은 회수하지 않습니다** |
| **지급 포인트 변경** | **심은 시점에 고정된 금액**으로 지급합니다. 진행 중인 작물에 **소급하지 않습니다.** 새로 심는 작물부터 적용됩니다 |

> **왜 소급하지 않나** — 정산 부채 원장이 심은 시점 금액의 합(`SUM(reward_points)`)으로 잡힙니다.
> 소급하면 과거 부채 스냅샷을 재현할 수 없어 "앞으로 지불할 금액" 집계가 무너집니다.
> `required_days`(작물 재배 일수)도 같은 이유로 심을 때 고정합니다.
> 근거: `design-01-schema.md:921-922`, `design-03-billing.md:136-139`
>
> **표시와 지급을 맞추려면** `GET /me/state`의 각 밭에 `rewardPoints`(심은 시점 고정 금액)를 내려주세요.
> 클라이언트는 이 값이 있으면 그걸 표시하고, 없을 때만 `/config`의 현재 금액으로 대신 보여줍니다.
> 아직 심지 않은 작물을 고르는 화면에서는 **현재 금액**을 보여줍니다(그게 실제로 적용될 값이므로).

## 1. 오늘의 미션 목록

> 🔴 **퀴즈농장은 단건 할당을 쓴다** (2026-07-31 지시): 앱에서 "미션 참여하기"를 누르면
> **한 건씩** 요청이 온다 — `POST /missions/assign`(아래 §1-1). 이 목록 API 는 구클라 호환으로 남긴다.

```
GET /missions
```

**응답 200**

```json
{
  "missions": [
    {
      "id": "quiz-tomato-price",
      "kind": "external",
      "title": "방울토마토 최저가 찾기",
      "description": "네이버쇼핑에서 방울토마토 최저가를 확인하고 오면 햇빛 2개를 받아요.",
      "reward": { "item": "sunlight", "count": 2 },
      "quiz": {
        "product": {
          "name": "유기농 방울토마토 1kg",
          "imageEmoji": "🍅",
          "imageUrl": "https://shop-phinf.pstatic.net/....png?type=f300"
        },
        "guide": [
          "아래 '참여하기'를 누르면 상품 페이지가 열려요.",
          "상품 정보에 있는 해시태그 중 3번째 태그를 확인해 주세요.",
          "다시 돌아와서 그 태그를 입력하면 돼요. #은 빼고 적어도 괜찮아요."
        ],
        "hintUrl": "https://sunny-5f1a8.rankfree.co.kr/s/kQgkslWgV6n",
        "question": "3번째 해시태그를 입력해 주세요",
        "placeholder": "예: 유기농",
        "tagIndex": 3,
        "tagCount": 6
      }
    }
  ]
}
```

**필드**

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | 미션 고유 ID |
| `kind` | `internal` \| `external` \| `attendance` | `external`은 외부 링크로 확인하는 미션 |
| `title` | string | 목록에 보이는 제목 |
| `description` | string | 목록·상세에 보이는 설명 |
| `reward.item` | `water` \| `sunlight` \| `fertilizer` \| `pesticide` | 지급 아이템 |
| `reward.count` | number | 지급 개수 |
| `quiz` | object \| 없음 | 없으면 참여만으로 완료(출석형) |
| `quiz.guide` | string[] | 참여 방법 안내. 번호가 매겨져 표시됨 |
| `quiz.hintUrl` | string \| 없음 | '힌트 보기'로 열리는 링크 |
| `quiz.question` | string | 질문 문구 |
| `quiz.placeholder` | string \| 없음 | 입력칸 안내 문구 |
| `quiz.tagIndex` | number \| 없음 | **몇 번째 해시태그**를 묻는지 (1부터). **사용자마다 다른 값** |
| `quiz.tagCount` | number \| 없음 | 상품에 달린 해시태그 개수 (예: 6개 중 3번째) |

> **`answer` 필드는 절대 응답에 포함하지 마세요.**
> 태그 목록(`tags`) 전체도 내려보내면 안 됩니다. `tagIndex`와 `tagCount`만 보냅니다.
> 자세한 규칙은 [2-2. 해시태그 랜덤 출제](#2-2-해시태그-랜덤-출제-체리피커-방지)를 보세요.

**서버가 판단할 것**
- 사용자별로 오늘 이미 완료한 미션은 제외하거나 `completed: true`로 표시
- 미션 노출 기간 / 활성 여부
- 광고주 캠페인 종료 시 자동 제외

## 1-1. 미션 단건 할당 🔴 (2026-07-31 — 퀴즈농장 기본 방식)

```
POST /missions/assign
```

앱에서 **"미션 참여하기"를 누를 때마다 한 건씩** 호출한다. 서버가 참여 가능한 미션 하나를 골라 내려준다.
미션 객체는 `GET /missions`의 배열 원소와 **완전히 같은 형태**라 클라이언트가 렌더링 코드를 공유할 수 있다.

**응답 200 — 할당됨**

```json
{
  "mission": { "id": "2", "title": "…", "quiz": { "tagIndex": 2, "tagCount": 3, "…": "…" }, "…": "…" },
  "meta": { "remaining": 3, "dailyLimit": 3, "slot": 3, "closed": false }
}
```

**응답 200 — 줄 미션이 없음** (오류가 아니다. 화면은 "남은 미션이 없어요")

```json
{ "mission": null, "meta": { "reason": "cooldown", "unlockAt": "2026-07-31T18:50:45+09:00", "remaining": 2 } }
```

| `meta.reason` | 뜻 | 화면 |
|---|---|---|
| `cooldown` | 쿨다운 중 (`unlockAt` 동봉) | 다음 참여 시각 안내 |
| `daily_limit` | 오늘 참여를 다 채움 | 내일 안내 |
| `closed` | 심야 휴지(02~06시, `opensAt` 동봉) | 오픈 시각 안내 |
| `no_mission` | 줄 미션이 없음 | "남은 미션이 없어요" |

**서버가 고르는 규칙** (design-04 §7): 현재 슬롯 잔여가 있는 미션만 → 사용자 상한을 채운 미션 제외 →
**소진율 낮은 미션 우선**(특정 미션만 먼저 끝나는 것 방지) → 동률은 **사용자별 결정적 셔플**.

> ⚠️ **할당은 예약이 아니다.** 받은 미션이 제출 시점엔 소진됐을 수 있다(그때는 `quota_full` 거절).
> 확정은 언제나 제출 시점의 원자 게이트가 한다. 소프트 차단 사용자에게는 사유를 주지 않고 `no_mission`으로만 답한다.

## 2. 정답 제출 (채점)

```
POST /missions/:missionId/submit
```

**요청**

```json
{ "answer": "12000" }
```

**응답 200 — 정답**

```json
{
  "correct": true,
  "reward": { "item": "sunlight", "count": 2 },
  "points": 100
}
```

> `points`는 **참여할 때마다 주는 포인트**입니다. 금액은 서버가 정합니다.
> 클라이언트는 이 값을 표시만 하므로, 정책이 바뀌어도 앱 재배포가 필요 없습니다.
> 포인트를 주지 않는 미션이면 필드를 생략하거나 `0`으로 보내면 됩니다.

**응답 200 — 오답**

```json
{
  "correct": false,
  "message": "다시 한 번 확인해 주세요."
}
```

**서버가 반드시 검증할 것**

1. **정답 일치** — 숫자만 남기고 정규화 후 비교 (`answer.replace(/[^0-9]/g, '')`)
2. **중복 지급 방지** — 이 사용자가 오늘 이 미션을 이미 완료했는지
3. **어뷰징 방지** — 제출 간격이 비정상적으로 짧은지, 시도 횟수 제한
4. **미션 활성 상태** — 종료된 미션이면 거부

정답 처리 시 서버에도 완료 기록을 남겨야 합니다. 클라이언트 저장소는 신뢰할 수 없습니다.

## 2-1. 참여 쿨타임 (2시간)

한 사람이 연달아 몰아서 참여하지 못하도록 **참여 사이에 2시간 간격**을 둡니다.
하루 3회 제한과 별개로 동작하며, 참여가 하루 중 여러 시간대로 흩어지는 효과도 있습니다.

### 서버가 내려주는 값

`GET /me/state` 응답에 다음 필드를 포함합니다.

```json
{
  "plots": [
    {
      "cropId": "tomato",
      "completedDates": ["2026-07-26", "2026-07-27"],
      "lastTendedDate": "2026-07-27",
      "rewardPoints": 150
    }
  ],
  "todayMissionIds": ["m_101"],
  "nextMissionAt": "2026-07-28T15:24:00+09:00",
  "cooldownNotify": true,
  "earnedPoints": 900,
  "harvested": ["lettuce"]
}
```

| 필드 | 의미 |
|---|---|
| `nextMissionAt` | 다음 참여가 가능해지는 시각 (ISO 8601). 지금 바로 가능하면 빈 문자열이거나 필드를 생략 |
| `cooldownNotify` | 쿨타임 종료 알림 수신 설정 ([2-3](#2-3-쿨타임-종료-알림-푸시)) |

`POST /missions/:missionId/submit` 응답에도 같은 필드를 함께 내려주면
클라이언트가 상태를 다시 조회하지 않아도 곧바로 안내를 갱신할 수 있습니다.

### 쿨타임 중에 제출이 들어오면

```json
{
  "correct": false,
  "message": "오후 3:24부터 다시 참여할 수 있어요",
  "nextMissionAt": "2026-07-28T15:24:00+09:00"
}
```

### ⚠️ 판정은 반드시 서버에서

클라이언트는 `nextMissionAt`을 **표시용으로만** 씁니다.
기기 시각은 사용자가 바꿀 수 있으므로, 제출 시점에 서버가
**마지막 참여 시각 + 쿨타임 ≤ 지금**을 다시 확인하고 아니면 거부해야 합니다.

- 기준 시각은 **서버 시각(Asia/Seoul)** 을 씁니다
- 쿨타임 길이는 서버 설정값으로 두고 코드에 상수로 박지 않습니다
  (클라이언트의 `MISSION_COOLDOWN_MINUTES`는 서버 응답을 못 받았을 때 쓰는 기본값입니다)
- 쿨타임 판정에 쓰는 "마지막 참여 시각"은 **참여 로그(append-only)** 에서 읽습니다

## 2-2. 해시태그 랜덤 출제 (체리피커 방지)

정답은 상품에 달린 **해시태그**입니다. 상품마다 보통 5~7개가 수집돼 있습니다.

### 문제

정답이 상품당 하나로 고정되면 **"이 미션 정답은 유기농"** 같은 공유가 돌고,
상품 페이지를 열지도 않은 사용자가 답만 입력하고 보상을 받습니다.
광고주에게 노출은 발생하지 않았는데 비용은 나가므로 **직접적인 손실**입니다.

### 해결 — 물어보는 태그 번호를 사용자마다 다르게

같은 미션이라도 A에게는 2번째 태그를, B에게는 5번째 태그를 묻습니다.
"정답은 유기농"이라는 공유가 다른 사람에게 쓸모없어집니다.

### 번호를 정하는 규칙

**서버가 결정합니다. 클라이언트가 정하면 아무 의미가 없습니다.**

```
tagIndex = 1 + (hash(userKey + missionId + 참여일) mod tagCount)
```

- **결정적(deterministic)이어야 합니다.** 목록을 다시 조회하거나 앱을 껐다 켜도 **같은 번호**가 나와야 합니다.
  매번 새로 뽑으면 사용자가 새로고침으로 쉬운 번호를 고를 수 있고(재추첨 어뷰징), 화면과 채점이 어긋납니다.
- 참여일을 섞으면 날이 바뀔 때 번호가 달라져, 같은 상품이 재등장해도 답을 재활용하지 못합니다.
- `hash`는 **서버 비밀키를 쓰는 HMAC-SHA256**을 권장합니다. 단순 `crc32`는 역산될 수 있습니다.

### 채점

제출된 문자열과 `tags[tagIndex - 1]`을 **정규화 후** 비교합니다.

| 단계 | 처리 |
|---|---|
| 1 | 앞뒤 공백 제거 |
| 2 | 맨 앞 `#` 제거 (여러 개면 전부) |
| 3 | 모든 공백 제거 |
| 4 | 소문자로 변환 |

클라이언트에도 같은 규칙(`normalizeTag`)이 있지만 **표시용**입니다. 판정은 서버가 다시 합니다.

### 남는 한계 — 솔직히 적어둡니다

태그 **전체 목록**이 공유되면 이 방식만으로는 뚫립니다. 공격 비용이 5~7배가 될 뿐입니다.
번호 랜덤화는 **"정답 하나만 공유"** 공격을 막는 장치이지 완전한 방어가 아닙니다.
아래를 함께 운영해야 합니다.

- **참여 토큰 검증** — 링크를 실제로 연 사용자에게 발급한 토큰이 있어야 제출을 받습니다
- **체류 시간** — 링크를 연 시각과 제출 시각의 차이가 비정상적으로 짧으면(예: 3초 미만) 보류
- **정답률 이상 탐지** — 첫 시도 정답률이 100%에 수렴하는 계정, 동일 IP·기기 군집
- **시도 횟수 제한** — 같은 미션에 하루 N회 이상 틀리면 그날은 차단 (전수 대입 방지)
- 적발 시 **보상 회수 + 참여 로그 보존** (append-only라 정산 근거가 남습니다)

## 2-3. 쿨타임 종료 알림 (푸시)

쿨타임이 끝나면 "다시 참여할 수 있어요" 알림을 보냅니다.

### 토스 알림의 구조

| 단계 | 담당 | 수단 |
|---|---|---|
| 동의 받기 | **클라이언트** | `requestNotificationAgreement({ options: { templateCode } })` |
| 발송 | **서버** | `POST https://apps-in-toss-api.toss.im/api-partner/v1/apps-in-toss/messenger/send-message` |

> ⚠️ **발송 API에 예약 파라미터가 없습니다.** 공식 문서도 "파트너사 서버에서 원하는 시점에 직접 호출"이라고 안내합니다.
> 따라서 **우리 서버가 `nextMissionAt` 시각에 맞춰 직접 호출**해야 합니다.

### 콘솔 사전 준비 (없으면 발송 자체가 불가)

1. **알림 동의문**을 먼저 만듭니다 (기능성 캠페인 생성 **전에**)
2. **기능성 캠페인**을 만들고 동의문을 연결 → `templateSetCode` 발급
3. **문구 검수 승인** — 승인 전에는 `sendTestMessage`조차 `5004`로 거부됩니다

우리 알림은 문서 분류상 *"재입고 알림 신청 / 이벤트 시작 알림 신청"* 과 같은
**알림 동의문이 필요한 유형**입니다. 동의 없이 보내면 캠페인 검수·운영 제재 대상입니다.

> `requestNotificationAgreement`는 `templateCode`, `sendMessage`는 `templateSetCode`로
> **이름이 다릅니다.** 같은 값인지 콘솔에서 확인이 필요합니다.

### 켜기 / 끄기 — 사용자가 언제든 바꿀 수 있어야 합니다

```
POST /me/notifications/cooldown
{ "enabled": true }   // 또는 false
```

`GET /me/state` 응답에도 현재 설정을 포함합니다. 기기를 바꿔도 따라가야 하므로 **서버가 원장**입니다.

```json
{ "cooldownNotify": true }
```

**⚠️ 토스 SDK에는 동의를 해제하는 API도, 동의 상태를 조회하는 API도 없습니다.**
`requestNotificationAgreement` 하나뿐입니다(52개 타입 정의 + `index.d.ts` 전수 확인).
따라서 역할을 이렇게 나눕니다.

| 대상 | 의미 | 바꾸는 곳 |
|---|---|---|
| **토스 알림 동의** | 이 미니앱이 알림을 보낼 **자격** | 한 번 동의하면 유지. 해제는 사용자가 **토스 앱 설정**에서 |
| **우리 서비스 수신 설정** (`cooldownNotify`) | 우리가 실제로 **보낼지 말지** | 미니앱 안의 토글 (언제든 on/off) |

- **끌 때는 토스 API를 호출하지 않습니다.** 우리 서버가 발송을 안 하면 끝입니다.
- 껐다가 다시 켤 때, 이미 동의한 사용자는 `alreadyAgreed`가 돌아오므로 동의 UI가 한 번 더 떠도 부담이 없습니다.
- 발송 직전 검증에 **`cooldownNotify === true`** 를 반드시 포함하세요. 예약을 걸어둔 뒤 사용자가 껐을 수 있습니다.

### 예약 구현 (rankfree)

이미 가동 중인 database 큐 + supervisor 워커 4개를 그대로 씁니다.

```php
// 미션 참여가 확정된 직후
NotifyCooldownEnded::dispatch($userId, $participationId)
    ->delay($nextMissionAt);
```

**발송 직전에 서버가 다시 확인할 것** — 예약해 둔 2시간 사이에 상황이 바뀔 수 있습니다.

- 알림 동의가 **아직 유효한지** (클라이언트 주장이 아니라 서버 기록으로)
- 그 사이에 **또 참여해서** 쿨타임이 새로 시작되지 않았는지
  → `participationId`가 그 사용자의 **최신 참여**와 일치할 때만 발송합니다
- **오늘 참여 횟수가 남아 있는지** — 3회를 다 썼으면 보내지 않습니다
- 참여 가능한 **미션이 실제로 남아 있는지** — 재고가 소진됐으면 보내지 않습니다

### 발송 물량 — 참여 건수와 같지 않습니다

**3회차 참여 뒤에는 보내지 않습니다.** 오늘 참여가 끝났으니 알릴 이유가 없습니다.
따라서 한 사람이 하루에 받는 알림은 **최대 2건**(1회차 후, 2회차 후)입니다.

```
알림 건수 = 참여 건수 − 그날 3회차를 채운 사용자 수
```

하루 참여 100만 건(= 사용자 약 33.3만 명 × 3회) 기준으로 **최대 66.7만 건**,
초당 약 7.7건입니다. 알림을 켠 사용자에게만 나가므로 실제로는 더 적습니다.

| 한도 | 값 | 우리 예상치 |
|---|---|---|
| 앱당 | 분당 15,000회 (초당 250건) | 초당 7.7건 = **3%** |
| 사용자당 | 분당 10회 | 하루 2건 |

한도는 여유롭습니다. 다만 쿨타임이 2시간 고정이라 **참여 피크의 2시간 뒤에 발송이 몰립니다.**
큐 워커 처리량은 실측 후 조정하고, 필요하면 발송 job에 분 단위 지터를 줍니다.

### 발송 시간대

**시간 제한 없이 즉시 발송합니다.** (사업자 결정)

> ⚠️ 쿨타임이 2시간이라 22시 참여 → 새벽 0시 발송이 발생합니다.
> 토스 문서에서 야간 발송 시간 제한 규정은 **확인하지 못했습니다.**
> 콘솔 문구 검수 단계에서 반드시 확인하고, 지적받으면 발송 창(예: 08~21시)을 도입하세요.
> 백엔드 설계(`design-02-runtime.md`)의 심야 휴지 02:00–06:00과는 별개로 동작합니다.

### 클라이언트 규칙

동의 UI는 **사용자가 '알림 받기'를 직접 누른 뒤에만** 띄웁니다.
진입 직후 자동으로 띄우면 정책상 다크패턴(`03-policy-and-review.md`)으로 분류돼 반려됩니다.

`VITE_NOTIFICATION_TEMPLATE_CODE`가 비어 있으면 알림 버튼 자체가 렌더링되지 않습니다.
콘솔 등록이 끝나면 값만 넣으면 동작합니다.

## 3. 일주일 완주 보너스

```
POST /reward/weekly
```

참여 일수를 모두 채웠을 때 **추가로** 지급하는 보너스입니다.
(미션 참여 포인트는 2번에서 이미 지급됨 → 여기는 완주 보너스만)

**요청 본문** — 없음 (`{}`). 참여일은 서버 기록으로만 판단합니다.

**응답 200**

```json
{ "ok": true, "points": 2000 }
```

**응답 200 — 지급 불가**

```json
{ "ok": false, "message": "이미 받은 보상이에요." }
```

**서버가 반드시 검증할 것**
- 서버에 기록된 참여일이 완주 조건을 채웠는지 (**클라이언트 값 신뢰 금지**)
- 이번 회차 보너스를 이미 받았는지
- **1인당 누적 최대 5,000포인트** 한도

  ⚠️ **밭이 3칸이라 하루 참여가 3번입니다.** 예전 공식은 하루 1회를 가정해 계산이 틀렸습니다.

  ```
  (참여 포인트 × dailyMissionLimit × 7일) + (수확 작물 포인트 합) ≤ 5,000
  ```

  | 예시 | 계산 | 결과 |
  |---|---|---|
  | 참여 100P · 하루 3회 · 7일 + 방울토마토 3개 수확(150P) | 100×3×7 + 150×3 = 2,100 + 450 | **2,550** ✅ |
  | 참여 300P · 하루 3회 · 7일 | 300×3×7 = 6,300 | **초과** ❌ |

  관리자 환경설정에서 금액을 올릴 때 이 식으로 교차검증해야 합니다.
  자세한 검증 규칙은 `farm-admin-settings.md`를 보세요.

  > ❓ **확인 필요** — 5,000P가 **프로모션 1건당 평생 누적**인지, 기간마다 리셋되는지 확인해야 합니다.
  > 평생 누적이면 위 예시(주당 2,550P)로도 **2주 만에 상한에 닿습니다.**
  > 상한에 닿은 사용자에게 무엇을 보여줄지(안내 문구·미션 노출 중단)도 함께 정해야 합니다.
- 1인 1회 제한 / 일일 제한 / 쿨다운

### 포인트 정책은 서버에만 둡니다

금액·일수는 바뀔 수 있으므로 클라이언트에 상수로 두지 않았습니다.
클라이언트는 서버가 내려준 `points` 값을 화면에 표시할 뿐이고,
`FALLBACK_CONFIG`(`src/game/features.ts`)는 서버 응답을 못 받았을 때
화면이 깨지지 않게 하는 최소 기본값입니다.

지급은 앱인토스 프로모션 서버 API(mTLS)로 호출합니다.
**사전 검수 2~3영업일 + 비즈월렛 최소 30만원 충전**이 선행되어야 합니다.

> ⚠️ 보상 조건은 **"7일 동안 매일 참여"** 입니다.
> "식물을 다 키웠으니 지급"으로 설계하면 **게임 결과 기반 보상**이 되어 프로모션 지급이 불가능합니다.
> 구현상 두 조건은 같지만, **정책 문서·심사 설명에는 반드시 '7일 참여'로 기술**하세요.

## 4. 관리자 — 미션·퀴즈 등록

운영자가 퀴즈를 직접 출제합니다. 아래는 미션 하나를 등록할 때 필요한 항목입니다.

```
POST   /admin/missions          미션 생성
PATCH  /admin/missions/:id      수정
DELETE /admin/missions/:id      삭제
GET    /admin/missions          목록 (비활성 포함)
```

**등록 폼 항목**

| 구분 | 항목 | 필수 | 설명 |
|---|---|---|---|
| 기본 | 제목 | ✅ | 목록에 보이는 이름 |
| 기본 | 설명 | ✅ | 한 줄 안내 |
| 기본 | 종류 | ✅ | 앱내완결 / 외부확인 / 출석 |
| 상품 | 상품명 | ✅ | 퀴즈 소재 상품 |
| 상품 | 이미지 | ✅ | 이모지 또는 이미지 URL |
| 안내 | 참여 방법 | ✅ | 여러 줄. 번호가 매겨져 표시됨 |
| 안내 | 힌트 링크 | – | 누르면 열릴 URL (외부확인형만) |
| 문제 | 질문 | ✅ | 예: "할인가는 얼마인가요?" |
| 문제 | **정답** | ✅ | **서버에만 저장. 응답에 절대 포함 금지** |
| 문제 | 단위 | – | 원 / 개 / 일 … 입력칸 접미사 |
| 보상 | 아이템 | ✅ | water / sunlight / fertilizer / pesticide |
| 보상 | 개수 | ✅ | 지급 개수 |
| 보상 | 포인트 | – | 없거나 0이면 아이템만 지급 |
| 노출 | 시작·종료 일시 | ✅ | 캠페인 기간 |
| 노출 | 활성 여부 | ✅ | 끄면 목록에서 제외 |
| 제한 | 1인 1일 참여 한도 | ✅ | 기본 1회 |

**정답 처리 규칙**
- 숫자만 남기고 비교합니다: `answer.replace(/[^0-9]/g, '')`
- 가격처럼 변동되는 값이 정답이면 **오차 허용 범위**를 두는 걸 권장합니다
  (예: 정답 ±5% 이내면 정답 처리) — 판매가는 수시로 바뀌기 때문입니다
- 정답이 바뀌면 미션을 수정하거나 비활성화하세요

**운영 시 주의**
- 출석형 미션에는 **포인트를 넣지 마세요.** 참여 없이 포인트를 주면 안 됩니다
- 포인트는 소액으로 유지하세요. 1인 누적 5,000P 한도 안에서 관리합니다
- 외부확인형 미션은 참여 시간이 길어 이탈률이 높습니다. 전체 미션 중 일부로만 두세요

```
VITE_API_BASE_URL=https://api.example.com
```

미설정 시 `src/api/mock.ts`의 목데이터로 동작합니다(로컬 화면 확인용).
