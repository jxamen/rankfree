# 리워드 참여시스템 백엔드 — rankfree 세션 인계

> 이 문서는 **진입점**이에요. 상세 설계는 중복해서 적지 않고 링크만 겁니다.
> 먼저 §3 문서 인덱스를 보고, §4의 Phase 0부터 시작하세요.

## 1. 무엇을 만드나

**대규모 리워드 참여시스템** 백엔드를 rankfree 안에 만듭니다. 첫 번째 매체가 토스 미니앱 **"퀴즈농장"** 이고,
같은 백엔드를 이후 **다양한 매체**에 제공할 계획입니다 (§7 정정 참고).

사용자는 밭 3칸에 작물을 심고 7일 동안 하루 한 번씩 돌봅니다. 돌보려면 **미션에 참여**해야 하는데,
미션은 rankfree의 **세부주문서(`marketing_order_items`)** 에서 나옵니다. 즉 광고주가 돈을 낸 건이고,
사용자가 상품 페이지에 방문해 **해시태그를 확인하고 입력**하면 참여가 확정됩니다.
7일을 채워 수확하면 **토스 포인트**를 지급합니다.

- 규모: 하루 수십만 ~ 100만 참여를 **산정 기준선**으로 설계. **100만은 상한이 아니며 그 이상으로 커질 수 있습니다**
- 수익: 참여 1건당 광고주 단가(스냅샷) − 사용자 지급 포인트
- **일 한도를 넘긴 참여는 청구할 수 없는 순손실**입니다. 초과 방지가 이 시스템의 최우선 요구사항입니다.

## 6. 절대 어기면 안 되는 것

1. **서버가 원장입니다.** 클라이언트가 보낸 참여일·횟수·금액을 믿지 마세요. localStorage는 사용자가 고칠 수 있습니다.
2. **정답(해시태그)을 응답에 넣지 마세요.** 태그 목록 전체도 금지. `tagIndex`와 `tagCount`만 내려줍니다.
3. **`tagIndex`는 서버가 결정적으로 정합니다.** `HMAC(userKey + missionId + 참여일) mod tagCount`.
   매번 새로 뽑으면 새로고침으로 쉬운 번호를 고르는 어뷰징이 생기고 화면과 채점이 어긋납니다.
4. **한도 차감은 원자적 조건부 UPDATE**로만. `WHERE used < daily_quota` + `affected_rows` 확인.
   읽고-계산하고-쓰면 동시 요청에서 초과가 납니다.
5. **소급 금지.** 작물 지급 포인트와 재배 일수는 **심을 때 스냅샷**하고 진행 중인 건에 적용하지 않습니다.
   부채 원장이 스냅샷 합계라 소급하면 과거 정산을 재현할 수 없습니다.
6. **1인 누적 5,000P 상한.** 참여 적립 + 수확 보너스 합산으로 검증하세요.
7. **참여 로그는 append-only.** 정산 근거이자 어뷰징 조사 근거입니다.
8. **설정 조회를 핫패스에서 매번 DB로 하지 마세요.** `SettingsServiceProvider`는 매 요청 `app_settings` 전 행을
   SELECT + 복호화하고 캐시가 없습니다. 별도 `FarmSettings` + 캐시 키 하나로 분리하세요 (`farm-admin-settings.md` §6).

## 7. 최근 정정 사항 (설계 문서보다 이게 최신)

- **규모 전제 (2026-07-31)** — "최대 100만"은 상한이 아닙니다. 설계 문서 곳곳의 100만/일 수치는 **용량 산정 기준선**이고,
  실제로는 그 이상으로 커질 수 있습니다. 파티션·캐시·인덱스·워커 등 용량 결정 시 기준선 초과 여지(headroom)를 확인하고,
  100만을 하드 리밋으로 박는 코드·설정을 만들지 마세요.
- **다중 매체 (2026-07-31)** — 퀴즈농장은 **첫 번째 매체**일 뿐, 이 백엔드를 다양한 매체에 제공할 계획입니다.
  참여·한도·정산·통계가 **매체(채널) 단위로 구분**될 수 있게 매체 식별자를 스키마·API에서 고려하고,
  퀴즈농장 전제(밭 3칸·7일·토스 포인트 등)를 공통 경로에 하드코딩하지 마세요.
- **네이밍 (2026-07-31)** — 이 시스템은 퀴즈농장 전용이 아니므로 시스템 명칭·구현 네이밍은 **reward(리워드 참여시스템) 계열**을
  씁니다. 설계 문서 본문의 `farm_*` 테이블·`Farm*` 클래스·`/farm` 라우트 표기는 작성 당시 이름이니, 구현 시
  **공통 리워드 코어(미션·참여·한도·쿨다운·포인트 원장·정산·통계)는 `reward_*`/`Reward*`/`/reward`** 로 치환하세요.
  단, 퀴즈농장 게임 전용 상태(밭·작물·심기·수확)는 매체 쪽 도메인이므로 farm 이름을 유지해도 됩니다.
- **환경설정은 매체(앱) 단위 (2026-07-31)** — 미니앱을 여러 개 운영할 계획이므로 환경설정(쿨타임·하루 참여 횟수·
  보상 포인트·심야 휴지 등)은 전역 단일이 아니라 **매체별로 각각** 설정할 수 있어야 합니다.
  `farm-admin-settings.md` 는 단일 앱 전제로 쓰였으니, 구현 시 설정 키·화면에 매체 스코프를 추가하세요.
- **`quantity` 의미 확정 (2026-07-31)** — `marketing_order_items.quantity` 는 **하루치(per_day)** 입니다.
  근거: rankfree 마이그레이션 `2026_07_23_200000_create_marketing_order_items_table.php` 주석 "그 날 수량(일수량)" —
  세부주문서는 기간형 주문을 회차(일) 단위로 쪼갠 것이라 행 자체가 하루치입니다. §8-4 해결, 운영자 확인 불필요.
- **벤더 개방 구조 (2026-07-31)** — 이 백엔드는 미니앱 전용이 아닙니다. **벤더를 추가하면 S2S API로
  미션(주문) 정보를 받아가고 그쪽에서 참여를 제출하는 개방형**입니다. 벤더 10곳 이상이 초당 수백~수천 건을
  동시에 보낼 수 있는 규모까지 수용해야 합니다. 아키텍처·API 계약·동시성·시간대 분산 송출·헤비유저/식별자
  한도·봇 감지는 전부 **`design-04-vendor-api.md`** 에 있습니다. Phase 3 코어(QuotaGate·참여 원장)는
  **매체 중립**으로 구현하세요.
- **벤더 ID 저장 위치 (2026-07-31)** — 벤더 ID는 `.env`(`FARM_VENDOR_ID`)가 아니라 **테이블·어드민 설정에 저장**합니다.
  미션 동기화 기준인 **"리워드 풀" 벤더 id는 시스템 설정**으로 지정하고(미지정이면 동기화 중단+알림),
  전용 배분 매체만 `reward_media.vendor_id`를 개별로 갖습니다(design-04 §2-1). 매체 추가는 배포 없이
  어드민에서. 이름 문자열 매칭 금지는 그대로 유지합니다.
- **배분은 3모드 (2026-07-31)** — 매체별 **처리 능력**도 **단가**도 다릅니다(특정 매체가 90%를 소진할 수도
  있고, 비싼 벤더만 계속 돌리면 마진이 무너집니다). 미션(상품)별 어드민 설정으로: `shared` 공유 풀
  선착순(기본) / `ratio` **비율 고정**(비싼 벤더 몫 제한, 저렴+적당 참여 벤더 비율 확보, 리밸런싱 시각 후
  미소진분 재개방 옵션) / `cost_priority` 단가 낮은 매체부터 워터폴. 매체별 max 상한·min 보장은 모드와
  독립, 계약 물량 매체만 전용 배분 — design-04 §2-1.
- **5,000P 재분류 (2026-07-31)** — 1인 5,000P는 사업 결정이 아니라 **토스 프로모션 정책 한도**입니다.
  누적 기준(평생/기간)은 토스 문서·콘솔에서 확인할 사항이지 사업자가 정하는 게 아닙니다.
  사업 입력으로 남는 것은 **지급 포인트**(참여 적립·수확 보상)이며, 이것도 매체별 설정 페이지에서 운영 관리합니다.
- **지급 포인트 소급 여부** — `server-api-spec.md`에 한때 "수확 시점 값"이라고 적혀 있었으나 **오류**였고,
  "심을 때 고정, 소급 없음"으로 수정했습니다(§6-5). 근거: `design-01:921-922`, `design-03:136-139`.
- **컬럼명 불일치** — 같은 값을 `design-01`은 `expected_crop_points`, `design-03`은 `reward_points`로 부릅니다.
  구현 전에 **하나로 통일**하세요. (`rankfree-integration.md` §5 Phase 3은 `reward_points`를 씁니다.)
- **5,000P 검증식** — 예전 식이 하루 1회 참여를 가정했습니다. 밭이 3칸이라 하루 3회입니다.
  `(참여 포인트 × dailyMissionLimit × 7일) + 수확 포인트 합 ≤ 5,000`
- **캐시 드라이버** — 로컬 개발 사본 `.env`는 `database`지만 **운영 서버는 `file`** 입니다. 운영 기준으로 설계하세요.
  파일 스토어는 **서버 로컬**이라 "기본 캐시 = 서버 간 공유"로 가정하면 안 됩니다. 공유가 필요한 값(C11 버전,
  L2 서킷 브레이커)은 `reward.cache.shared_store`(기본 `database`)에 둡니다 — design-02 §7-4·§7-5.
- **엔진 차이 함정: MariaDB의 `UPDATE ... SET`은 좌→우 평가 (2026-07-31 실측)** — 앞에서 갱신한 컬럼을
  뒤 표현식이 **갱신된 값으로** 봅니다. sqlite는 전부 원본 값으로 평가합니다. 그래서
  `SET completed_days = completed_days + 1, status = CASE WHEN completed_days + 1 >= required_days ...`는
  **운영(MariaDB)에서만** 하루 일찍 확정되고, 테스트(sqlite)로는 절대 잡히지 않습니다.
  → 같은 UPDATE 안에서 **방금 갱신한 컬럼을 다시 참조하지 말고 PHP가 계산한 값을 바인딩**하세요.
  로컬 MySQL 8.4로 리워드 테스트를 한 번 돌려보면(`DB_CONNECTION=mysql …`) 이 계열 결함이 드러납니다.
- **동기화 카운터는 오늘 것만 고치면 안 된다 (2026-07-31)** — `ensureDailyCounters`가 익일 행을
  `insertOrIgnore`로 **선생성**하므로, 한도 변경을 "오늘 행"에만 반영하면 다음 농장일 06:00부터 전량 대조까지
  낡은 한도가 집행됩니다(C12가 전제한 5분 창이 아니라 최대 2시간). `stat_date >= 오늘`로 갱신합니다.
- **정답은 운영자가 입력하지 않는다 (2026-07-31 지시)** — 미션 정답은 **상품 해시태그**(`spi.seller_tags` 스냅샷)이고,
  출제 번호(`tagIndex`)는 사용자×미션×날짜로 결정되며, **문제 표시와 답 입력은 퀴즈농장(매체) 쪽**에서 합니다.
  rankfree 어드민에 "정답 입력 화면"은 필요 없습니다. 따라서 미션 승격 조건은 `answer` 유무가 아니라
  **채점 가능 여부**(태그가 있거나 고정 정답이 있으면 active — `MissionSync::isGradable`)입니다.
  태그 없는 상품은 채점 근거가 없어 draft로 남습니다(경고 로그).
- **퀴즈농장은 발주 벤더로 등록한다 (2026-07-31 지시)** — `vendors`에 "퀴즈농장"(channel=`api`)을 만들고
  그 id를 `app_settings 'reward.pool_vendor_id'`로 지정합니다. 이 벤더로 배분된 세부주문서만 미션으로
  미러링되고, 미션 리스트는 **JSON API로 넘깁니다**(미니앱 `/api/farm/missions`, 벤더 `/api/v1/missions`).
  ⚠️ `OrderDispatchService`는 전송 결과를 그대로 세부주문서 status로 쓰고(`api_url`이 비면 `failed`),
  MissionSync는 `status='sent'`만 미러링합니다 — **퀴즈농장 수신 URL을 벤더 설정에 넣어야 발주가 sent가 됩니다.**
- **스케줄 뮤텍스는 커맨드+옵션 단위 (2026-07-31)** — `reward:sync-missions --incremental`과
  `reward:sync-missions`는 서로 다른 락이라 같은 시각에 동시 실행됩니다(같은 미션 upsert 경합 → unique 위반으로
  그 주기 동기화가 통째로 중단). 전량 대조를 5분 격자 밖(08:02)으로 옮겨 회피합니다.

## 9. 콘솔 의존 — 이게 없으면 못 하는 것

토스 개발자센터 작업은 **사업자만** 할 수 있고 리드타임이 있습니다.

| 콘솔 작업 | 막히는 기능 |
|---|---|
| **`appName` 확정 + 앱 등록** (수정 불가) | CORS 도메인, 그 아래 전부 |
| **mTLS 클라이언트 인증서** | 토스 API 호출 **전부** (포인트 지급·알림) |
| Outbound 방화벽 `117.52.3.192`·`211.115.96.192`·`106.249.5.192`:443 | 동일 |
| 프로모션 등록 + 검수(2~3영업일) + 비즈월렛 충전 | 포인트 지급 |
| 알림 동의문 → 기능성 캠페인 → `templateSetCode` → 문구 검수 | 쿨타임 종료 알림 |

**인증서 없이도 Phase 0~3(참여 확정 경로)까지는 만들 수 있습니다.** 포인트 지급과 알림만 나중에 붙이세요.
