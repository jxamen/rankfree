# design-04 — 벤더 개방 구조와 대량 동시 요청 (2026-07-31)

> 이 백엔드는 미니앱 전용이 아니다. **벤더를 추가하면 주문(미션) 정보를 제공받고, 벤더 쪽에서 참여를 일으켜
> 우리에게 제출하는 개방형 구조**다. 벤더가 10곳 이상이 되면 초당 10·100·1,000건씩 동시에 참여 요청이
> 들어올 수 있고, 이를 전부 수용(정확히 수락하거나 정확히 거절)할 수 있어야 한다. — 2026-07-31 사용자 지시
>
> design-01(스키마)·02(런타임)·03(정산)의 코어는 유지된다. 이 문서는 그 위에 **매체 계층**과
> **대량 동시성 계층**을 추가한다. 충돌 시 이 문서와 HANDOFF §7이 우선.

## 1. 매체 2유형 아키텍처

| 유형 | 예 | 사용자·UI·보상 운영 | 우리 백엔드가 하는 일 |
|---|---|---|---|
| `miniapp` (first-party) | 퀴즈농장 | **우리가** 운영 (밭·작물·토스 포인트) | 미션 공급 + 채점 + 쿼터 + 사용자 상태 + 포인트 + 정산 |
| `vendor_api` (외부 벤더) | 타사 리워드앱·오퍼월 등 | **벤더가** 자기 사용자에게 운영 | 미션 공급(S2S) + 쿼터 + 참여 접수·검증 + 벤더 정산 |

**공통 코어는 하나다**: 미션 풀 → 쿼터 게이트 → 참여 원장 → 정산.
퀴즈농장의 해시태그 채점·밭·포인트는 miniapp **어댑터**의 일이고, 쿼터 게이트(`QuotaGate`)와 참여 원장은
매체가 무엇이든 **단일 경로**를 지난다. 매체별 분기를 코어에 넣지 않는다 (HANDOFF §7 다중 매체 정정).

```
광고주 주문(marketing_orders)
  └ 세부주문서(marketing_order_items — 일×벤더, quantity=그날 그 벤더 몫)
      └ 미션 미러(reward_missions)
          ├ miniapp 어댑터: 퀴즈농장 API(server-api-spec.md) → 채점 → ┐
          └ vendor_api 어댑터: 벤더 S2S API(이 문서 §3) ──────────────┴→ QuotaGate → 참여 원장 → 정산
```

## 2. 기존 구조와의 접점

- **기존 (일×벤더) 배분과의 관계** — `marketing_order_items`는 하루 수량을 관리자 배분 비율(`product_vendors`)로
  업체별로 쪼갠 (일 × 벤더) 단위다(2026-07-23 개정, 코드 확인). 이는 **푸시 발주(외주 대행)용 정적 배분**이고,
  리워드 매체에는 그대로 쓰지 않는다 — §2-1의 공유 풀이 기본이다.

### 2-0. 미션 타입 체계 🔴 (2026-08-01 지시 — 미구현, 다음 단계)

> 미션 내용은 **플레이스 방문·저장·쇼핑 등 타입에 따라 다 다르다. 동일 미션이라도 로직이 다른 경우도 있다.**

기존 서비스(boosting_shop `quiz`)의 실제 타입을 조사한 결과가 근거다 — 하나의 "쇼핑 미션" 안에도 서로 다른
수행 절차와 **정답 소스**가 공존한다:

| 타입(예시) | 수행 | 정답 소스 |
|---|---|---|
| 쇼핑 · 해시태그 | 검색 유입 → 상품 상세 → 관련 태그 확인 | **태그 N번째**(참여자별 랜덤) — 현재 구현됨 |
| 쇼핑 · 상품번호 | 검색 유입 → 상세정보 → 구매 추가정보 | 상품번호 **앞 5자리** |
| 쇼핑 · 가격비교 | 가격비교 → 판매처에서 스토어·판매가 일치 상품 | 상품번호 앞 5자리 |
| 쇼핑 · 찜하기 | 상품 찜 → 화면 캡처 업로드 | 이미지 AI 판정 |
| 자사몰 | 검색 유입 → 상품/고객센터 | 상품 URL 또는 전화번호 |
| 플레이스 · 방문/저장 | 플레이스 유입 → 저장·길찾기 등 | 캡처 또는 별도 확인 |

**설계는 [design-05-mission-types.md](./design-05-mission-types.md) 에 따로 정리했다**(2026-08-01 — 타입 확정은 나중,
구조만 먼저). 요지: `kind`(대분류) + `variant`(세부 로직) 2단으로 나누고, variant 마다
정답 소스·필요 데이터·문구 세트·응답 필드를 capability 로 묶는다. 배분(§2-1)이 타입 단위로 걸리므로
**타입 확정이 배분 구현보다 먼저**다.

⚠️ 지금 구현된 것은 **쇼핑 · 해시태그 하나뿐**이고, 문구 세트도 `shopping_tag`/`fallback` 둘이다.
상품번호형은 채널 상품번호(`shop_product_infos.channel_product_id`)를 미션에 저장하지 않아 **불가** —
지원하려면 컬럼 추가가 선행되어야 한다.

**쇼핑 미션 안내 표기 규칙 (2026-08-01 확정, 구현됨)**: 참여자가 같은 상품을 정확히 찾아야 하므로
안내에 **상품 사진 · 상품명 · 판매가**를 함께 내려준다(응답 `quiz.product` 의 `imageUrl`·`name`·`price`,
상점명 `shopName`, 검색어 `keyword`). 원본 서비스도 "아래 정보와 같은 상품을 찾아주세요" 카드로 같은 3종을 쓴다.

### 2-1. 배분 모델 — 3가지 모드 🔴 (2026-07-31 정정)

> 매체별 **처리 능력**(사용자 수)도, **단가**(참여 1건당 지급액)도 크게 다르다. 특정 매체가 전체의 90%를
> 소진할 수도 있지만, **비싼 벤더가 참여를 잘 낸다고 물량을 다 가져가게 두면 마진이 무너진다** —
> 저렴하면서 참여가 어느 정도 나오는 벤더의 비율을 고정할 수 있어야 한다.

구조는 공통이다: vendors에 **"리워드 풀" 벤더 1행**(channel=`reward`)을 두고 광고주 상품 배분
(`product_vendors`)에서 리워드 채널 몫을 정한다. 그 몫(세부주문서의 일수량)을 매체들에게 어떻게 나누느냐가
**배분 모드**이고, 미션(상품)별로 오버라이드할 수 있는 어드민 설정이다:

| 모드 | 동작 | 언제 쓰나 |
|---|---|---|
| `shared` 공유 풀 (기본) | 전 매체 선착순 — 사용자 많은 매체가 자연히 많이 가져감(90%도 가능) | 매체 단가가 비슷하거나 소진 극대화가 우선일 때 |
| `ratio` **비율 고정** | 매체별 % 캡 = 일수량 × 비율. **리밸런싱 시각**(예: 20시) 이후 미소진분은 공유 풀로 재개방(옵션) | **단가가 다른 매체 믹스** — 비싼 벤더의 몫을 제한하고, 저렴+적당 참여 벤더의 비율을 확보 |
| `cost_priority` 단가 우선 | 지급 단가 낮은 매체부터 슬롯을 개방하고, 슬롯 목표 미달분만 다음 단가 매체로(워터폴) | 마진 최적화를 자동으로 — 저가 매체가 못 채우는 만큼만 비싼 매체 사용 |

- `ratio`의 미소진 처리: 리밸런싱 시각까지는 비율을 지키고, 그 후 남은 물량은 공유 풀로 풀어 **일수량
  미달(광고주 이행 실패)을 막는다.** 재개방 없이 비율 엄수도 옵션(매체 설정).
- 🔴 **어드민 요구 (2026-08-01)**: "벤더1에 **어떤 미션을 어떤 비율로** 지정할지"를 화면에서 설정할 수 있어야 한다.
  즉 배분은 전역 모드만이 아니라 **매체 × 미션(또는 미션 타입) 단위 비율표**로 다룬다.
  구현 시 필요한 것: ① `reward_media_allocations(media_id, mission_id|kind, mode, ratio, max_per_day, min_per_day)`
  ② 노출·할당 시 그 매체의 캡을 카운터 차원에 추가(미션×매체) ③ 어드민에서 비율 합계 검증(100% 초과 경고).
  **미구현** — 현재는 전 매체 공유 풀(`shared`)로만 동작한다.
- **매체별 max 상한·min 보장**은 모드와 독립적으로 걸 수 있다(신규 벤더 30% 상한, 계약 물량 보장 등).
- **전용 배분(예외)**: 계약상 물량을 보장해야 하는 매체만 자기 vendors 행을 따로 갖고 `product_vendors`에서
  직접 배분받는다(`reward_media.vendor_id` 지정). 이 경우 그 매체의 카운터는 자기 세부주문서 행이다.
- **마진 가시성**: 매체별 지급 단가가 다르므로 일 정산 집계(§5)에 매체별 마진(광고주 단가 − 지급 단가)을
  노출한다 — 배분 비율을 조정하는 근거 데이터.
- 동시성 영향: 모드가 무엇이든 판정은 **원자 카운터 연산 하나**다 — `ratio`/`cost_priority`는 카운터 키에
  매체 차원이 추가될 뿐(미션×매체 캡), 공유 풀은 미션 단위 카운터 하나. 카운터가 미션(주문×일) 단위로
  샤딩되고 Redis 원자 연산(§4-2 ③)은 미션당 수만 QPS를 처리하므로 문제가 없다. DB 폴백 시에도
  행 하나의 원자적 조건부 UPDATE로 동일하게 안전하다.
- **기존 푸시 발주와 공존**: `vendors.channel`에 `reward`를 추가한다. 이 채널의 벤더는 order_dispatches로
  푸시 전송하는 대신 **미션 풀 편입**이 곧 "발주"다(스케줄러가 due 회차를 `sent` 처리하는 의미는 유지).
  기존 api/gsheet 벤더는 종전 흐름 그대로.
- **매체 테이블 `reward_media`** (HANDOFF §7 정정의 앵커 — 벤더 ID는 .env 아님):

```php
Schema::create('reward_media', function (Blueprint $t) {
    $t->id();
    $t->string('name', 120);
    $t->string('type', 20);                       // miniapp | vendor_api
    $t->foreignId('vendor_id')->nullable()->constrained('vendors')->nullOnDelete(); // 전용 배분 매체만(§2-1) — 공유 풀 매체는 NULL
    $t->foreignId('api_user_id')->nullable();     // vendor_api: API 키 소유 회원(users) — scope 게이트와 연결
    $t->unsignedInteger('rate_limit_rps')->default(100);   // 벤더별 초당 요청 상한(§4-2 ①)
    $t->unsignedInteger('payout_unit_price')->default(0);  // 참여 1건당 벤더 지급 단가(원) — 정산 입력(§5)
    $t->string('verify_mode', 20)->default('server');      // server(우리 채점) | vendor(벤더 자율+사후 감사)
    $t->json('settings')->nullable();             // 매체별 환경설정(쿨타임·하루횟수·작물포인트 등 — miniapp용은 여기)
    $t->boolean('is_active')->default(false);
    $t->timestamps();
});
```
  미션 동기화 필터의 기준은 **"리워드 풀" 벤더 id**(시스템 설정, 어드민 지정 — §2-1)이고, 미지정이면 동기화가
  **중단 + 알림**한다. 전용 배분 매체(§2-1)는 자기 `vendor_id` 행이 추가 필터가 된다. 이름 문자열 매칭 금지
  (vendors.name unique 없음).

## 3. 벤더 API 계약 v1 (scope: `mission`)

### 3-0. 미션 제공 2방식 (2026-07-31 지시)

| 방식 | 흐름 | 대표 매체 |
|---|---|---|
| **리스트(오퍼월)** | 목록을 열면 미션이 쭉 나옴 → 골라서 **클릭** → 서버가 ①실존 ②참여 가능 상태(활성·슬롯 잔여·사용자 자격) 검증 → 가능하면 **상세 정보 리턴** → 수행 → 정답 제출 | 오퍼월(offerwall)·외부 벤더 |
| **단건 할당(미니앱)** | "미션 참여하기"를 누르면 서버가 **미션 하나를 골라 정보만 내려줌** → 화면 출력 → 수행 → 정답 제출 | 퀴즈농장 등 미니앱 |

- 제출 이후는 두 방식이 **완전히 동일**하다: 미션별 정답 체크 → 맞으면 맞다고 리턴 + **참여자 정보 기록**
  (쿼터 게이트·원장 — 코어 단일 경로 §1).
- **상세 조회는 스냅샷이지 예약이 아니다.** 클릭 검증을 통과해도 제출 시점에 소진됐을 수 있다 —
  확정은 언제나 제출 시점의 원자 게이트가 한다(선점(홀드)은 Phase 11 옵션, design-02 §C1 주변).
- 상세 응답에도 정답·태그 목록은 절대 넣지 않는다(`tagIndex`·`tagCount`만 — HANDOFF §6).
- 매체 유형과 직교한다: vendor_api 매체도 단건 할당을 쓸 수 있고, 미니앱도 리스트를 쓸 수 있다.
  `reward_media.settings`의 `serve_mode`(`list`|`single`)로 정한다.

**구현 상태 (2026-07-31)** — 선택 로직은 `MissionAssigner` 하나로 두 매체 유형이 공유한다:

| 경로 | 엔드포인트 | 상태 |
|---|---|---|
| 미니앱 단건 (**퀴즈농장 기본**) | `POST /api/farm/missions/assign` | ✅ 구현 — server-api-spec §1-1 |
| 미니앱 리스트 | `GET /api/farm/missions` | ✅ 구현 (구클라 호환으로 유지) |
| 벤더 리스트 | `GET /api/v1/missions` + `GET /api/v1/missions/{id}` | ✅ 구현 |
| 벤더 단건 | `POST /api/v1/missions/assign` | ✅ 구현 — 줄 미션이 없으면 `204` + `Retry-After`(사유 비공개 §8) |

**공개 문서는 광고주용과 분리한다** (2026-07-31 지시) — 대상 독자가 다르다:
`/developers`(광고주 — 데이터·주문)와 별개로 **`/developers/reward`(매체 파트너 — 미션 수신·참여 제출·정산 대조)**.
본문은 [partials/reward-api-doc](../../resources/views/partials/reward-api-doc.blade.php), 페이지는
[site/developers-reward](../../resources/views/site/developers-reward.blade.php).
⚠️ 공개 문서 예제에는 **실제 미션의 정답 태그·광고주 상품명을 절대 넣지 않는다**(가상 예시 값 사용).

인증은 **기존 API 키 인프라 재사용** ([28_ORDER_API](../28_ORDER_API.md) — Bearer `rk_…`,
활성/만료/허용 IP/일일 한도, `users.api_scopes` 3중 게이트). `ApiKey::SCOPES`에 `mission`만 추가한다.

| 엔드포인트 | 용도 | 비고 |
|---|---|---|
| `GET /api/v1/missions` | 미션 목록(리스트 방식 §3-0) | `remaining`은 **현재 슬롯 잔여**(§7 — 하루 전체 아님). `?participant_hash=` 옵션(§8 소프트 차단 반영 피드). **ETag + 3~5초 캐시** — 폴링 부하 흡수 |
| `GET /api/v1/missions/{id}` | **클릭 검증 + 상세**(리스트 방식 §3-0) | ①실존 ②active ③슬롯 잔여 ④`participant_hash` 자격(쿨다운·한도·소프트차단) 검증 후 상세 리턴. 불가면 `410 gone` \| `422 {reason}` |
| `POST /api/v1/missions/assign` | **단건 할당**(단건 방식 §3-0) | 자격 검증 후 참여 가능한 미션 1건을 골라 상세로 리턴. 없으면 `204` |
| `POST /api/v1/missions/{id}/participations` | 참여 제출 | **`Idempotency-Key` 헤더 필수** + `participant_hash`(벤더측 사용자 식별 해시) 필수 |
| `GET /api/v1/participations?date=` | 벤더 정산 대사 | 일자별 수락 건수·집계 |

**참여 제출 응답 규약** — 벤더는 이 응답만 믿고 자기 사용자에게 보상하면 된다:

- `200 {status:"accepted", participation_id, remaining}` — 수락(빌링 카운트됨). **키는 snake_case 확정**
  (2026-07-31 구현 정정 — 초기 구현의 `participationId`는 폐기. 멱등 응답 스냅샷이 DB에 저장되므로 출시 전에 통일)
- `200 {status:"duplicate", participation_id}` — 같은 Idempotency-Key 재시도 → **첫 응답 그대로 재반환**
- `422 {status:"rejected", reason}` — `quota_full` | `slot_exhausted`(+`retry_after_seconds`, §7) | `closed` |
  `participant_duplicate` | `verify_failed` | `not_eligible`(§8 — 세부 사유 비공개) …
  (REJECT_REASONS는 design-02 목록에 벤더용을 추가해 공유)
- `429 + Retry-After` — rate limit 초과. 벤더는 백오프 후 **같은 Idempotency-Key로** 재시도
- 5xx — 같은 키로 재시도 (멱등 보장이 있으므로 중복 카운트 없음)

정답(해시태그 등) 비노출 원칙은 벤더 API에도 동일하다. `verify_mode=server` 미션은 채점 입력만 받고
정답·태그 목록을 절대 반환하지 않는다.

## 4. 대량 동시 요청 설계 🔴 (핵심)

### 4-1. 목표 수치와 "수용"의 정의

- 설계 기준선: **정상 500 RPS, 순간 버스트 10,000 RPS** (벤더 10곳 × 최대 1,000 req/s — 상한 아님, 그 이상 확장 경로 포함)
- "수용" = 모든 요청에 **정확한 동기 응답**(수락/거절/429)을 준다는 뜻이지, 전부 즉시 수락한다는 뜻이 아니다.
  한도 초과는 청구 불가 순손실이므로 **초과 0이 처리량보다 우선**한다.
- 벤더별 `rate_limit_rps`는 **계약이자 보호 장치** — 총합이 인프라 상한을 넘지 않게 어드민에서 관리한다.

### 4-2. 4계층 방어 (요청이 안쪽으로 갈수록 비싸다)

```
① 벤더별 토큰버킷 (Redis)        → 초과분 429 + Retry-After     ~0.1ms
② L1 soldout 캐시 (프로세스, 2~5s) → 소진 미션 즉시 422           0ms (Redis도 안 감)
③ Redis 원자 카운터 (Lua 1회)     → 수락/quota_full 판정          ~0.3ms   ← 진실 카운터
④ DB (비동기 배치)               → 참여 원장 영속화 + 대사        요청 경로 밖
```

- **③이 초과 방지의 진실이다.** `(mission_id, date)` 잔여 카운터를 06:00 일 시작(또는 첫 요청)에 DB에서
  `SETNX`로 로드하고, Lua 스크립트 한 번으로 「잔여>0이면 DECR+수락, 아니면 거절」을 원자 실행한다.
  단일 Redis에서 이 연산은 수만 QPS를 처리한다 — 벤더 10곳 버스트에도 카운터 정합이 깨지지 않는다.
- 카운터는 **미션(주문×일) 단위로 샤딩**된다(§2-1) — 공유 풀에서 여러 매체가 같은 미션에 경합해도
  Redis 원자 연산은 미션당 수만 QPS를 처리하고, 활성 미션이 많을수록 경합은 더 분산된다.
- design-02 C8의 **DB 2단 UPDATE 게이트는 그대로 유효하다** — `QuotaGate` 인터페이스 뒤의 드라이버가
  DB(소규모)냐 Redis(대량)냐의 차이. Phase 3은 DB 드라이버로 시작하고, 벤더 트래픽이 붙기 전에
  Redis 드라이버로 승격한다(전환 스위치는 config).

### 4-3. 동기 응답, 비동기 영속화

- 수락/거절 **응답은 동기**(③의 결과). 참여 기록은 Redis Stream(`XADD`) → 큐 워커가 **배치 INSERT**
  (100~500건 단위) — DB 쓰기가 요청 경로에서 빠지므로 버스트에 DB가 병목이 되지 않는다.
- at-least-once + 멱등 upsert(`unique(media_id, idempotency_key)`)로 중복 기록을 막는다.
- Redis는 **AOF everysec** — 최악 1초 유실 가능성은 일 마감 대사(④)가 검출·보정한다(카운터 vs 원장 비교,
  불일치 알림). 참여 로그 append-only 원칙(design-03)은 그대로.
- **Redis 장애 시 degraded mode**: ③을 DB 2단 UPDATE(C8)로 폴백하고 전 벤더 rate limit을 자동 하향
  (총 ~350 QPS — design-02 실측 상한). 처리량을 희생해도 **초과 0을 유지**한다. fail-open 금지.

### 4-4. 멱등성

- `Idempotency-Key`(벤더 생성, UUID)는 Redis `SETNX`(TTL 24h)로 1차 차단, DB unique로 2차 백스톱.
- 키 재사용 요청은 **첫 응답을 그대로 재반환**(Redis에 응답 스냅샷 저장). 5xx·타임아웃 재시도 폭풍에도
  카운터가 두 번 줄지 않는다.
- 🔴 **거절보다 멱등이 우선**(2026-07-31 구현 정정): 재시도가 첫 요청의 *커밋 전에* 도착하면 1차 조회는
  빈손이고, 첫 요청이 커밋된 뒤 참여자 한도(`per_user_limit`)에 걸려 `participant_duplicate` 422가 나간다 —
  서버는 수락·과금했는데 벤더는 거절로 기록하는 정산 불일치. 그래서 **한도 거절을 응답으로 내보내기 직전에
  멱등키를 한 번 더 조회**하고, 저장된 응답이 있으면 `duplicate` 200으로 되돌린다(카운터 불변).
  단위 테스트로 재현 불가한 경합이라 Phase 10 부하 시나리오(재시도 폭풍)의 검증 항목으로 남긴다.
- 벤더측 사용자 중복은 `participant_hash` 기준 `(mission_id, participant_hash, date)` unique 백스톱
  (1차 통제는 벤더 책임, 우리는 최종 방어 + 품질 지표).

### 4-5. 인프라 경로

- 현재 단일 서버(63.8GB RAM·**Swap 0**): Redis 도입(design-02 I14와 동일 결론 — 대량 목표엔 필수),
  php-fpm `pm.max_children` 상향 + **벤더 API 전용 풀 분리 검토**(미니앱 사용자 트래픽과 격리 — 벤더 버스트가
  퀴즈농장 응답을 밀어내지 않게). 워커·캐시 상한은 OOM 계산 필수.
- **수평 확장 경로**: 앱은 스테이트리스(카운터·멱등키·rate limit 전부 Redis 중앙)라 **웹서버 증설만으로 확장**된다.
  DB는 배치 쓰기라 병목이 늦게 오고, 오면 원장 테이블 파티션(Phase 9)과 리드 분리로 대응.
- 10,000 RPS를 단일 PHP-FPM이 실시간 처리하는 건 비현실적 — 그래서 ①의 계약 rate limit이 총량을 다듬고,
  초과분은 429 재시도로 **시간축에 펴서** 받는다. 인프라를 늘리면 rate limit을 올리는 구조.

### 4-6. 신뢰·어뷰징 모델

- `verify_mode=server`: 참여마다 채점 payload를 우리가 검증(퀴즈농장과 동일 경로).
- `verify_mode=vendor`: 벤더 자율 + **사후 감사** — append-only 원장, 벤더별 품질 지표(거절률·중복률·
  소진 후 시도율·participant_hash 분포)를 일 집계해 어드민 노출. 이상 벤더는 rate limit 하향·정지·정산 차감 근거.

## 5. 정산 — 벤더 차원 추가

- 참여 1건 = 빌링 단위(불변). **수익 = 광고주 단가 스냅샷 − 벤더 지급 단가**(`reward_media.payout_unit_price`,
  참여 시점 스냅샷 — 소급 금지 원칙 동일).
- design-03의 5분 증분 배치·부채 원장·일 마감 확정을 그대로 쓰고, 집계 차원에 `media_id`를 추가한다
  (벤더별 일 정산 = 벤더 대사 API(§3)의 소스).
- miniapp 매체의 "지급"은 토스 포인트(수확 시), vendor_api 매체의 "지급"은 벤더 정산 — 코어 원장은 같고
  지급 어댑터만 다르다.

## 7. 시간대 자연 분산과 송출 🔴 (2026-07-31 지시)

> 세부주문서 일수량이 50건이면 연달아 다 소진되면 안 된다. 실제 사람들이 활동하는 시간대·비율로
> 나눠 배정해야 자연스럽다. 세부주문서가 많으면 이를 감안해 뽑아오고 송출해야 한다.

**기반은 design-02 §5의 슬롯 체계다** — 하루를 시간 구간(슬롯)으로 나누고, 시간대별 활동 비율 곡선의
누적 상한(`slot_cap`, C1 공식)까지만 그 시점 참여를 허용한다. 심야(02~06시) 휴지 포함.
여기서는 그 체계를 **벤더 송출까지** 확장한다:

- **피드의 `remaining` = 현재 슬롯 잔여**(`slot_cap − used`). 하루 전체 잔여를 노출하지 않는다 —
  벤더가 50건을 10분에 몰아치는 것 자체가 불가능해진다.
- **슬롯 잔여 0인 미션은 피드에서 제외**(소진과 동일하게 보임). 제출이 와도 `slot_exhausted` +
  `retry_after_seconds`(다음 슬롯 개방까지)로 거절 — QuotaGate가 일 한도와 슬롯 상한을 함께 판정한다.
- **세부주문서가 많을 때의 송출 규칙**: 현재 슬롯 잔여가 있는 미션만 + **소진율 낮은 미션 우선**(진행률
  균형 — 특정 미션만 먼저 끝나는 것 방지) + 벤더·페이지별 결정적 셔플(HMAC — 같은 미션이 항상 맨 위에
  노출돼 몰리는 것 방지) + 페이지네이션.
- 시간대 비율 곡선은 **매체 설정으로 조정 가능**(기본: design-02 §5 분포). 매체마다 사용자 활동 패턴이
  다를 수 있다.
- miniapp(퀴즈농장)도 동일 — 원래 design-02가 미니앱 기준으로 설계한 것이고, 벤더 API가 이를 물려받는 것.

🔴 **미니앱과 벤더의 슬롯 판정이 다르다**(2026-07-31 구현 확정 — 헷갈리기 쉬운 지점):

| 경로 | 슬롯 상한 초과 시 | 근거 |
|---|---|---|
| miniapp | **수락**하고 `slot_overflow=true` 로 기록(C8 2단 UPDATE) | 사람이 직접 푼 참여라 청구 가능. 거절하면 매출을 버린다 |
| vendor_api | **거절** `slot_exhausted` + `retry_after_seconds` (`QuotaGate::consumeWithinSlot`) | 스크립트가 몰아치는 축이라 분산 자체가 무의미해진다 |

`retry_after_seconds`는 현재 슬롯 종료까지, 마지막 슬롯(심야 휴지 직전)이면 다음 농장일 06:00까지
(한도가 그때 리셋되므로) — `SlotCap::secondsToNextSlot()`.

## 8. 헤비유저·식별자 기반 참여 제한 🔴 (2026-07-31 지시)

> 특정 사용자의 참여가 과도하면 "남은 미션이 없습니다"로 차단할 수 있어야 한다. 헤비유저를 잘 막아야 한다.
> IP·ADID 등 식별 가능한 정보로 재참여 횟수를 제한하는 **설정**도 필요하다.

**식별자 한도 (매체 설정으로 임계 조정 — 하드코딩 금지)**

| 식별자 | 한도 축 | 기본 제안 | 비고 |
|---|---|---|---|
| 사용자 키(`participant_hash`/`x-user-key`) | 미션당 재참여 · 일 참여 수 · 7일 누적 | 미션당 1회 / 일 3회 | 기존 farm_users 카운터·`(mission, uid, date)` unique 확장 |
| **IP** | 일 참여 수 · 미션당 참여 수 | 일 10회 | design-02 C10 `daily_ip`·`ip_limit` 확장. 통신사 NAT 오탐 주의 — 끄기 옵션 유지 |
| **ADID**(광고 식별자) | 미션당 재참여 · 일 참여 수 | 미션당 1회 | 미니앱·벤더가 제출 payload에 `adid_hash`(sha256)로 전달. 계정 갈이 방어 |
| 디바이스 핑거프린트(확장 여지) | 〃 | — | 필요 시 추가 — 식별자 테이블을 **타입 확장 가능**하게 설계 |

- 스키마: `reward_identity_counters (media_id, id_type, id_hash, scope[mission|day], scope_key, used, attempts, updated_at)` —
  식별자 원문은 저장하지 않고 **해시만**(개인정보 최소화). 카운터 차감은 참여 확정 트랜잭션과 동일한
  원자적 조건부 UPDATE, 대량 경로에서는 Redis 카운터(§4-2 ③)와 같은 계층에서 판정.
  🔴 **사전 COUNT 검사만으로는 한도가 지켜지지 않는다**(2026-07-31 구현 확정): 같은 IP 뒤의 서로 다른
  사용자는 사용자 행이 달라 락 직렬화가 없어 전원이 "29 < 30"을 보고 통과한다. 그래서 사전검사는 사유
  안내용이고, 진짜 한도는 확정 트랜잭션 안 `IdentityGate::consume`(조건부 UPDATE → INSERT 2-step)이 지킨다.
  락 순서는 사용자 → 사용자×미션 → 식별자 → 미션 일 한도(가장 뜨거운 공유 행을 마지막에 가장 짧게).
- **시도(오답·거절)도 식별자 축에 누적한다**(`attempts`, 매체 설정 `ip_attempt_limit` 기본 300) —
  계정(`participant_hash`)을 갈아치우면 사용자 축 시도 한도가 초기화되므로, 정답 브루트포스를 막는 축은
  IP다. 벤더 경로에도 사용자 축 시도 한도(`daily_attempt_limit`)를 적용한다 — **오답이 공짜면
  `verify_mode=server`(우리가 검증)라는 전제 자체가 무너진다**.
- **읽기 엔드포인트는 참여자 행을 만들지 않는다**: `GET /missions?participant_hash=`는 조회만 하고 없으면
  개인화를 건너뛴다(폴링만으로 `reward_users`를 무한히 늘릴 수 있었다). 미니앱의 `x-user-key`는 클라이언트
  자유 발급이라 **신규 행 생성만 IP 시간당 예산**(`reward.new_user_per_ip_hourly`, 기본 60)으로 제한한다 —
  요청 자체를 스로틀하면 통신사 NAT 뒤의 정상 사용자가 함께 막힌다.
- 한도 초과의 표현이 핵심 — **오류가 아니라 "없음"**:

**소프트 차단 원칙** — 어뷰저에게 판정 정보를 주지 않는다

- miniapp: 차단 대상에게 `GET /missions`가 **빈 목록**을 반환 — 화면엔 "남은 미션이 없습니다"
  (정상 소진과 구분 불가). 명시적 차단 오류를 절대 내보내지 않는다.
- vendor_api: `GET /missions?participant_hash=`로 사용자별 피드를 뽑으면 차단 유저에겐 빈 목록.
  피드 없이 제출만 오면 `not_eligible`(세부 사유 비공개 — 내부 로그·어드민에만 기록).
- 판정 입력: 식별자 한도(위 표) + 리스크 스코어(§9). 차단·해제·화이트리스트는 어드민에서.

## 9. 자동화(봇) 어뷰징 감지·차단 🔴 (2026-07-31 지시)

> 프로그램으로 자동으로 포인트를 빼먹는 곳까지 생긴다 — 감지해서 막을 수 있어야 한다.

**신호 (리스크 스코어 가중 합, 배치 계산)**

- 제출 간격의 균일성(사람은 불규칙) · 피드 조회→제출 간격이 초인간적으로 짧음(기존 `too_fast` 확장)
- 24시간 연속 활동 · 심야 휴지 우회 시도 집중
- 정답률·즉답률 비정상(항상 정답 + 항상 즉시)
- IP·ADID·핑거프린트 클러스터(다계정 공유) · 신규 계정 대량 생성 패턴
- 벤더 단위 이상(§4-6 품질 지표): 특정 벤더의 participant_hash 분포·거절률 급변

**대응 3단계**

1. **실시간 룰**(요청 경로): `too_fast`·식별자 한도(§8)·rate limit — 기존 REJECT_REASONS 체계
2. **배치 스코어링**(시간별): 위 신호를 점수화 → 임계 초과 시 **자동 소프트 차단**(§8 방식 — "남은 미션 없음")
   + 어드민 검토 큐(승인·해제·화이트리스트). 판정 이력은 `reward_risk_*` 테이블에 보존
3. **지급 게이트**: miniapp은 지급이 수확(7일 완주) 시점 1회라 **지급 전에 걸러낼 시간이 구조적으로 있다**
   (design-01의 강점 유지) — 수확 시 리스크 재검증 후 지급. vendor_api는 정산 차감·벤더 품질 지표로 소급.

- 참여 로그 append-only(기존 원칙)가 조사·소급의 근거. 스코어 계산은 로그 기반이라 요청 경로에 부하 없음.
- 토스 미니앱 환경은 캡차 삽입이 어려우므로 **서버 판정 중심**, 클라이언트는 타이밍 신호만 보탠다.
