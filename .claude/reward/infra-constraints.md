## 캐시 전략 (확정)

### 결론: **APCu + MariaDB**. Redis는 도입하지 않음

API 서버가 **1대**이므로 서버 간 캐시 공유가 필요 없습니다.
이 조건에서는 APCu가 Redis보다 유리합니다.

| | APCu | Redis |
|---|---|---|
| 별도 데몬 | **없음** (PHP 확장) | 있음 — **뻗을 서버가 존재** |
| 장애 시 | php-fpm과 생명주기 공유 | 별도로 죽고 별도로 복구 |
| 복구 | `systemctl restart php83-php-fpm` | 데이터 복구 시도 → 실패 가능 |
| 지연 | 메모리 직접 접근 (μs) | 네트워크 왕복 |
| 설치 | `dnf install php83-php-pecl-apcu` | 데몬 설치·설정·감시 |

> **과거 장애 이력**: 카페24에서 Redis가 다운되고 복구도 불가능해 크게 고생한 적이 있음.
> 원인 추정 — Redis가 원장이라 카운터 소실 시 복원 불가.
> APCu는 **뻗을 데몬 자체가 없고**, 원장은 MariaDB에 있으므로 같은 상황이 발생하지 않음.

**Redis는 API 서버를 2대 이상으로 늘릴 때** 도입합니다.
그전에 미리 넣으면 장애 지점만 하나 늘어납니다.

### 계층 구조

```
읽기:  L1 APCu(프로세스 공유 메모리)  →  L2 MariaDB(원장)
쓰기:  MariaDB 원자적 UPDATE 만 사용  (캐시를 거치지 않음)
```

### 원칙

1. **캐시는 가속기일 뿐 원장이 아니다.**
   APCu가 비어도 DB에서 재구축됩니다. 복구 = fpm 재시작.

2. **읽기와 쓰기를 분리한다.**

   | 구분 | 양 | 처리 |
   |---|---|---|
   | 읽기 (목록·카운터 확인·쿨다운 판정) | 참여의 10~100배 | **APCu** |
   | 쓰기 (참여 확정·수량 차감) | 하루 100만 = **초당 12건** | **MariaDB 원자적 UPDATE** |

   부하 대부분은 읽기입니다. 쓰기 초당 12건은 MariaDB가 여유롭게 처리합니다.
   쓰기까지 캐시로 옮기면 캐시 소실 = 카운터 소실이 되어 위험합니다.

3. **캐시 장애 시 저하 모드로 계속 동작한다.**
   APCu가 비면 DB 폴백. 느려지지만 멈추지 않고 카운터도 안 틀어집니다.

4. **php-fpm 재시작 시 APCu가 초기화**됩니다.
   초기화 후 첫 요청들이 DB를 치므로, 배포 직후 캐시 워밍이 필요합니다.

### 쓰기 경로 (정확성 보장)

```sql
UPDATE mission_daily_counter
   SET used = used + 1
 WHERE mission_id = ? AND stat_date = ? AND used < daily_limit;
-- affected_rows = 1 → 슬롯 확보 성공
-- affected_rows = 0 → 한도 소진, 거부
```

경쟁 조건이 원천적으로 없습니다. 동시 요청이 와도 하나만 성공합니다.

**hot row 대비**: 인기 미션에 요청이 몰리면 같은 행에 락이 걸립니다.
미션당 N개 샤드 행으로 나누고 사용자 키 해시로 샤드를 고르며, 잔여 확인은 합계로 봅니다.
(샤드 개수는 설계서에서 확정)

## 대역폭 설계

### 미션 이미지는 외부 링크 — 우리 대역폭 0 (확정)

미션에 표시하는 상품 이미지는 **외부 CDN을 직접 참조**합니다.
세부주문서에 들어 있는 이미지 URL을 그대로 내려주므로 **우리 서버 대역폭은 소모되지 않습니다.**

가용 대역폭: Rocky 1,300GB + 카페24 800GB·500GB = **월 2,600GB**
→ 이미지를 우리가 서빙하면 월 6TB가 필요해 초과하지만, 외부 참조라 해당 없음.

### 다만 이미지 크기는 정규화한다 (사용자 체감 개선)

네이버 CDN은 `type` 파라미터로 리사이즈를 제공합니다. **실측값**:

| type | 용량 | 비고 |
|---|---|---|
| `o1000` | **252 KB** | 1000px 원본 |
| `m510` | 96 KB | |
| **`f300` / `w300`** | **40 KB** | 110px 표시에 충분 — **채택** |
| `f120` | — | 404, 미지원 |

우리 비용은 0으로 동일하지만 **사용자가 받는 용량이 6배** 차이납니다.
하루 100만 건이면 사용자 전체가 252GB를 받느냐 40GB를 받느냐의 차이이고,
모바일 데이터 사용자의 로딩 체감이 크게 달라집니다.

- **서버**: 미션 응답을 만들 때 이미지 URL의 `type`을 `f300`으로 정규화
- **클라이언트**: 방어적으로 `src/lib/image.ts`의 `thumbnailUrl()`에서 한 번 더 변환 + `loading="lazy"`

### 카페24 2대 = 백업 경로

평상시 트래픽이 거의 가지 않습니다. 아래 상황에서만 씁니다:
- 외부 CDN이 핫링크를 차단할 때 → 이미지 프록시·캐시
- 원본 이미지가 사라졌을 때 → 캐시본 서빙
- API 서버 대역폭이 한계에 닿을 때 → 정적 자산 오프로드

## 설치가 필요한 것

```bash
# APCu (Remi 저장소, php83용)
dnf install php83-php-pecl-apcu
systemctl restart php83-php-fpm

# php.ini 권장값 (/etc/opt/remi/php83/php.d/40-apcu.ini)
apc.enabled=1
apc.shm_size=256M        # 미션 목록 + 카운터 사본 기준. 사용량 보고 조정
apc.ttl=7200
apc.enable_cli=0
```

⚠️ 배포 문서에는 *"root SSH 불가(sudo는 httpd 명령만 NOPASSWD)"* 로 기록되어 있어
supervisor도 `pip3 install --user`로 우회 설치했습니다.
사업자는 현재 **root 권한이 있다**고 확인했으므로 위 설치가 가능합니다.
불가할 경우 대안은 **파일 캐시 + OPcache**이며, 성능은 떨어지지만 동작은 합니다.

## Laravel 설정 변경

```env
CACHE_STORE=apc          # 현재 database → apc
SESSION_DRIVER=database  # 유지 (세션은 영속성이 중요)
QUEUE_CONNECTION=database # 유지 (워커 가동 중)
```

⚠️ `.env` 변경 후 **반드시** `php83 artisan config:cache` 실행 (config 캐시 상태라 안 하면 반영 안 됨).

## 미확인 사항

- 실 서버의 `apcu`·`opcache` 설치 여부 (로컬 CLI PHP 8.3.30에는 둘 다 없음)
- php-fpm 풀 설정 `pm.max_children = 20` — 하루 100만 건 기준 상향 필요 여부 검토
- 카페24 2대의 실제 사양과 접근 방식 (SSH? FTP만?)
